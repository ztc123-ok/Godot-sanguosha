# 《三国杀》双人版角色技能功能 Agent 提示词

> 使用方式：将下面“可直接复制的完整提示词”整体交给编码 Agent。  
> 本提示词基于当前工程已有的基础牌、15 种锦囊、装备、距离、AI、UI 和 `RuleSmokeTest`，新增武将与技能系统，不要求从零重建工程。

## 预设范围

- “身份”和“武将”是两个独立概念：`role_name` 继续表示主公/反贼，新增 `general_id`、`general_name`、`kingdom` 和武将技能。
- 首批实现 9 名武将：曹操、张辽、许褚、关羽、张飞、赵云、甘宁、孙权、吕布。
- 暂不实现主公技、限定技、觉醒技、使命技、转换技、双将、国战、阵亡武将更换和多于两名玩家，也不为这些未使用类型预建枚举、状态和空实现。
- 技能规则采用本提示词中的“双人版明确裁定”，不混用其他年份或其他模式的规则文本。

## 可直接复制的完整提示词

~~~text
你是资深 Godot 4.6 游戏开发者，使用纯 GDScript 4.x。

工程目录：{PROJECT_DIR}
Godot 控制台程序：{GODOT_EXE}

请在当前《三国杀》双人版工程上新增“武将选择与角色技能系统”。这是一项增量开发任务：先完整检查现有工程、场景、脚本、测试、README、ARCHITECTURE 和 Git 状态，再修改；不得覆盖重建工程，不得回退与本任务无关的现有改动。

一、必须保持的现有基线

1. 兼容 Godot 4.6 stable 和 GDScript 4.x，不使用 Godot 3.x 语法、废弃 API、第三方插件或伪代码。
2. Main 只负责绑定 GameManager 与 UIManager。
3. GameManager 继续作为牌堆、阶段、响应、判定、伤害、濒死、胜负、技能结算和 AI 行为的唯一规则入口。
4. Player/BattlePlayer 只保存角色领域状态，不直接驱动流程。
5. UIManager 只显示状态并调用 GameManager 的 request/can_* 接口，不直接修改武将、体力、手牌、装备、技能次数或流程状态。
6. 玩家与 AI 的所有操作都必须通过相同的 GameManager 公共请求接口。
7. 原有基础牌、15 种锦囊、全部装备、距离、连环、属性伤害、无懈、判定、濒死和 AI 流程必须继续通过现有测试。
8. 延迟 AI 行为继续携带 match/action generation；重新开始或重新选将后，旧回调必须失效。
9. 每个技能的发动、放弃、代价、目标、转化牌和结算结果都同时输出 print 日志和界面对局日志。

二、领域模型与目录

新增下列目录和脚本；名称可以按现有命名风格微调，但职责不可混淆：

scripts/generals/
- GeneralDefinition.gd：不可变武将定义，至少包含 id、display_name、kingdom、max_hp、skill_ids。
- GeneralFactory.gd：按 id 创建全部武将定义，提供默认武将和可选武将列表。

scripts/skills/
- Skill.gd：技能基类，至少包含 id、display_name、description、activation_mode、skill_tags、usage_scope、max_uses，以及默认无副作用的规则钩子。
- SkillFactory.gd：按 skill_id 创建技能对象。
- SkillUseContext.gd：一次主动/响应用牌上下文，记录使用者、实体牌代价、有效牌类型、来源技能、目标、是否虚拟牌。
- DamageContext.gd：一次伤害上下文，记录来源、目标、数值、属性、来源实体牌、有效牌类型、原因、是否连环传播。
- DrawContext.gd：摸牌阶段上下文，记录原始摸牌数、最终摸牌数和替代摸牌技能。
- generals/ 下为每个武将技能的独立脚本，禁止把所有技能硬编码为 GameManager 中按武将名判断的巨大 match/if。

首批技能分类只实现实际需要的最小集合：

- `ActivationMode.ACTIVE`：由操作者主动发动，例如【制衡】。
- `ActivationMode.TRIGGERED`：满足明确时机后询问是否发动，例如【奸雄】【突袭】【裸衣】。
- `ActivationMode.VIEW_AS`：将实体牌按另一有效牌使用或打出，例如【武圣】【龙胆】【奇袭】。
- `ActivationMode.MODIFIER`：持续修正规则参数或响应需求，例如【咆哮】【无双】。
- `SkillTag.LOCKED`：锁定技，不询问是否发动，满足条件时必须应用，例如【咆哮】【无双】。
- `UsageScope.UNLIMITED`：没有技能自身的发动次数限制，但仍服从卡牌、阶段、距离、目标等原规则。
- `UsageScope.PER_TURN`：每回合按 `max_uses` 限制，例如【制衡】每个出牌阶段所在回合限一次。

上述维度不得压缩成一个互斥的 `skill_type`：发动方式与技能标签含义不同。例如【无双】属于 `MODIFIER + LOCKED`，【制衡】属于 `ACTIVE + PER_TURN`。首批武将不涉及限定技、觉醒技、主公技、使命技和转换技，因此不要添加对应枚举、计数器、FlowState、UI 标记或占位脚本。以后真正加入相关武将时再按实际规则扩展。

各技能的分类必须参与真实规则，而不只是 UI 文本：

- `activation_mode` 决定由主动请求、触发队列、视为牌入口还是规则修正器处理；
- `LOCKED` 决定技能不得显示“发动/不发动”确认；
- `usage_scope` 与 `max_uses` 决定 GameManager 的合法性检查及回合重置；
- UI 根据分类显示“主动技”“触发技”“视为技”“锁定技”和“每回合限一次”等状态；
- AI、玩家和自动化测试共用相同的分类与合法性判断。

建议的技能钩子至少覆盖：
- 回合开始、阶段开始前、阶段结束后；
- 计算摸牌数/替代摸牌阶段；
- 主动技能可用性和代价；
- 将实体牌转换为另一种有效牌；
- 使用牌前、指定目标后、需要响应时、牌结算后；
- 造成伤害前、受到伤害后；
- 计算攻击范围、距离、出杀次数、手牌上限；
- 武将重置和每回合技能次数重置。

不要让 Skill 脚本直接修改手牌、体力、装备、牌堆或 FlowState。技能只声明可用性、修正规则或向 GameManager 产生结构化结算请求；实际状态修改仍由 GameManager 完成。

BattlePlayer 新增并正确重置：
- general_id、general_name、kingdom；
- skills: Array[Skill]；
- turn_skill_usage: Dictionary；
- match_skill_usage: Dictionary；
- 技能所需的明确状态标记，例如“裸衣本回合生效”，不得把含义不同的标记复用。

`role_name` 仍只表示“主公/反贼”，UI 和日志不得把身份名称覆盖成武将名称。

三、卡牌生命周期和虚拟牌

为支持【奸雄】和转化技，必须明确实体牌生命周期：

1. 实体牌从手牌/装备区支付后进入“处理中/结算区”，不能在效果尚未完成时立即永久进入弃牌堆。
2. 牌的整条效果、响应、伤害和濒死链结束后，再把仍在处理区的实体牌移入弃牌堆。
3. 若【奸雄】等效果取得该实体牌，则从处理区移入获得者手牌，后续不得重复进入弃牌堆。
4. 虚拟牌本身不进入牌堆；它只引用一张或多张真实代价牌。真实代价牌按照统一生命周期进入处理区并在结算后弃置。
5. 不得临时改写真实 Card 的 `card_type` 来伪装转化牌。使用 `SkillUseContext.effective_card_type` 或等价字段。
6. 装备区的牌作为技能代价时，必须调用现有统一“失去装备”入口，以正确触发白银狮子等离场效果。
7. DamageContext 必须贯穿普通伤害、火焰伤害、雷电伤害、连环传播、【杀】、【决斗】和锦囊伤害；不得只向技能传一个伤害数值。

四、技能流程状态与授权

在现有 FlowState 基础上增加必要的明确状态，至少能表达：
- GENERAL_SELECTION：开局选择武将；
- SKILL_CONFIRM：询问是否发动可选触发技；
- SKILL_SELECT_CARDS：选择技能代价牌；
- SKILL_SELECT_TARGET：选择技能目标；
- SKILL_RESOLVING：技能正在结算，防止重复提交；
- MULTI_RESPONSE：处理【无双】要求的多张响应牌；也可以用更明确的等价状态。

GameManager 必须保存：
- skill_owner：技能拥有者；
- skill_actor：当前实际操作者；
- pending_skill：正在处理的技能；
- pending_skill_cards/targets；
- response_required_count 和 response_received_count；
- 成功、取消、无合法目标、无合法代价各分支的 continuation。

每个 request_skill_* 接口必须检查：当前 FlowState、skill_actor、技能归属、阶段、次数、代价和目标是否合法。不能只用 `current_player().is_ai` 作为总拦截，因为受到伤害、响应和选项的操作者可能不是当前回合角色。

技能结算结束后必须清空上下文并精确返回：
- 原出牌阶段；
- 原响应流程；
- 摸牌阶段队列；
- 伤害/濒死队列；
- 或游戏结束状态。

五、首批武将及双人版裁定

实现以下 9 名武将。每个技能使用独立脚本，并显示技能名与完整说明。

1. 曹操，魏，4 体力
   - 奸雄（触发技，`TRIGGERED + UNLIMITED`）：每次受到一次伤害后，若造成此次伤害的实体牌仍在结算区，可以选择获得该牌。
   - 连环传播伤害没有独立实体牌时，不重复获得来源牌；同一实体牌最多被一名角色获得一次。
   - AI：只要可获得牌就发动。

2. 张辽，魏，4 体力
   - 突袭（触发技，`TRIGGERED + UNLIMITED`）：摸牌阶段，可以放弃本次正常摸牌，改为获得对手一张手牌。
   - 双人版只有一名其他角色，所以最多获得一张；对手无手牌时不可发动。
   - 玩家只知道对手手牌数量，随机获得其中一张，不显示未获得的暗牌。
   - AI：对手有手牌时发动。

3. 许褚，魏，4 体力
   - 裸衣（触发技，`TRIGGERED + UNLIMITED`）：摸牌阶段，可以令本次摸牌数 -1；若如此做，直到本回合结束，自己使用【杀】或【决斗】造成的伤害 +1。
   - 最终摸牌数不得小于 0；伤害加成在 DamageContext 的伤害前修正阶段处理。
   - AI：手中有【杀】、【决斗】或能转化出【杀】且存在合法目标时发动。

4. 关羽，蜀，4 体力
   - 武圣（视为技，`VIEW_AS + UNLIMITED`）：可以将一张红色手牌或红色装备牌当【杀】使用或打出。
   - 必须支持出牌阶段、南蛮响应、决斗响应和借刀杀人响应。
   - 仍受攻击范围和每回合出杀次数限制；装备作为代价时走统一失去装备入口。

5. 张飞，蜀，4 体力
   - 咆哮（锁定技，`MODIFIER + LOCKED + UNLIMITED`）：出牌阶段使用【杀】无次数限制。
   - 不改变攻击范围，也不绕过合法目标、响应、护甲、伤害和濒死流程。

6. 赵云，蜀，4 体力
   - 龙胆（视为技，`VIEW_AS + UNLIMITED`）：可以将【杀】当【闪】、将【闪】当【杀】使用或打出。
   - 当【闪】使用【杀】时只适用于需要【闪】的响应；当【杀】使用【闪】时适用于主动出杀以及所有需要【杀】的响应。
   - 转化后的牌仍使用原实体牌作为代价，且遵守有效牌类型对应的次数、距离和响应规则。

7. 甘宁，吴，4 体力
   - 奇袭（视为技，`VIEW_AS + UNLIMITED`）：出牌阶段，可以将一张黑色手牌或黑色装备牌当【过河拆桥】使用。
   - 必须复用原【过河拆桥】的目标校验、无懈链、区域选择和弃置逻辑。
   - 装备作为代价时先走统一失去装备入口；不能选择同一实体牌同时作为代价和被拆目标。

8. 孙权，吴，4 体力
   - 制衡（主动技，`ACTIVE + PER_TURN`，`max_uses = 1`）：出牌阶段限一次，可以弃置至少一张自己的手牌和/或装备牌，然后摸等量的牌。
   - 支持多选、取消和确认；确认前不支付代价。
   - 失去装备走统一入口，摸牌复用 GameManager.draw_cards。
   - AI：若手牌超过当前体力，或存在其评估为低价值的牌，则选择低价值牌发动一次；不得空选或死循环。

9. 吕布，群，4 体力
   - 无双（锁定技，`MODIFIER + LOCKED + UNLIMITED`）。
   - 吕布使用【杀】指定对手后，对手需要连续打出两张【闪】才抵消；少一张或主动放弃都视为未闪避。
   - 吕布作为【决斗】的一方时，对手每轮需要连续打出两张【杀】；吕布自己每轮仍只需要一张【杀】。
   - 八卦阵每次成功判定只视为一张【闪】；丈八蛇矛每次发动只视为一张【杀】。
   - 多张响应期间必须保留已响应数量，不能在第一张后提前结算，也不能重复造成伤害。
   - AI 能完成两张响应、使用转化技/装备响应，或在不足时明确放弃。

六、选将、开局与重新开始

1. 开局先进入 GENERAL_SELECTION，不立即发初始手牌。
2. 玩家从 9 名武将中选择一名；AI 从剩余武将中随机选择，默认不与玩家重复。
3. 提供“开始对局”请求；只有双方武将已确定才初始化牌堆、按武将 max_hp 设置体力并各摸 4 张牌。
4. 为自动化测试和快速运行保留确定性的默认配置，例如 Player1=曹操、Player2=吕布；测试不得依赖随机武将。
5. 重新开始默认沿用上一次双方武将；另提供“重新选将”回到 GENERAL_SELECTION，并使旧 AI 回调失效。
6. 测试可以通过公开的 setup/start 接口直接指定双方 general_id，不得通过直接篡改私有状态绕过初始化。

七、UI 要求

1. 在 1280×720 内增加选将面板，显示武将名、势力、体力上限、技能名和技能说明。
2. 对局中双方角色区同时显示：身份、武将名、势力、体力、技能名、技能当前可用/已用状态。
3. 主动技能和转化技必须有明确按钮或技能入口；只在当前操作者可合法发动时可见/可用。
4. SKILL_CONFIRM 显示“发动/不发动”；选牌类技能支持选择、取消和确认，并显示已选数量及合法性。
5. 武圣、龙胆、奇袭需要先点技能再选代价牌，或使用同等清晰的交互；不得让普通点击实体牌产生歧义。
6. 无双的响应提示必须显示“需要 2 张，已响应 0/1/2 张”。
7. 对手暗手牌仍只显示背面和数量；突袭不能泄露其内容。
8. 技能选择层不能遮死必需的手牌、目标、响应按钮和日志；手牌过多仍可横向滚动。
9. UI 所有动作只调用 request_*，刷新只订阅 state_changed/log_added。

八、AI 要求

1. AI 与玩家共用技能可用性、代价、目标和结算入口，禁止另写一套直接改状态的“AI 专用技能规则”。
2. AI 必须能：
   - 在选择武将后正常开局；
   - 按各技能规则发动或放弃可选技能；
   - 使用武圣、龙胆、奇袭形成的虚拟牌；
   - 使用制衡并避免空选/重复调用；
   - 正确处理无双的两张【杀】/【闪】响应；
   - 在任何技能分支无合法牌或目标时安全返回，不让状态机停住。
3. 所有延迟技能动作检查 generation、当前 FlowState 和 skill_actor；状态已变化时静默失效。

九、测试要求

保留并继续执行原 `tests/RuleSmokeTest.tscn`。新增 `tests/SkillSmokeTest.gd` 与 `tests/SkillSmokeTest.tscn`，或在不降低可读性的前提下扩展现有测试。

测试必须确定性构造牌堆、花色和手牌，至少逐项覆盖：

1. GeneralFactory 能创建 9 名武将，id 唯一，技能脚本存在，体力上限正确。
2. 每个技能的 `activation_mode`、`skill_tags`、`usage_scope` 和 `max_uses` 与本提示词一致；首批范围中不存在未使用的限定技、觉醒技、主公技、使命技或转换技类型。
3. 身份与武将字段独立；指定武将开局后双方各摸 4 张，体力取武将上限。
4. 重新选将后旧 AI 回调不再执行。
5. 奸雄：普通【杀】伤害后可获得来源实体牌；放弃则牌进弃牌堆；同一牌不能重复获得。
6. 突袭：对手有手牌时放弃正常摸牌并只获得一张；无手牌时不可发动。
7. 裸衣：少摸一张；本回合【杀】和【决斗】伤害 +1；下回合失效。
8. 武圣：红色手牌和红色装备分别能当【杀】主动使用、AOE/决斗响应；黑牌不可用。
9. 咆哮：同一出牌阶段能合法使用两张【杀】，但仍受距离限制。
10. 龙胆：【闪】当【杀】主动使用与响应、【杀】当【闪】响应；实体牌只结算一次。
11. 奇袭：黑牌可进入完整【过河拆桥】与无懈流程；红牌不可用；装备代价正确触发离场规则。
12. 制衡：多选手牌和装备，弃 N 摸 N，每回合只能一次，取消不支付代价。
~~~
